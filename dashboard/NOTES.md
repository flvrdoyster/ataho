# 대시보드 노트

대시보드(`dashboard/`, `scripts/ga4_*.py`)의 결정 근거·함정·남은 과제. 코드에는 설명을 두지 않고 여기에 모은다.
수치는 대시보드와 GA에서 본다 — 여기엔 분석에서 얻은 판단만 적는다.

## 0. 게임 스타일 입히기 — 다음 차례
밑작업은 끝났다(2026-08-10 시작, 2026-08-14 박스 개편으로 갱신). 보이는 값은 전부 `dashboard/theme.css`의
토큰 한 곳에 있고, `dashboard.css`(구조)와 `dashboard.js`(차트)는 그 값을 읽기만 한다. `--w`는 순위 표 행마다
JS가 인라인으로 주는 막대 길이라 토큰이 아니다.

입히는 방법: theme.css를 복사해 `theme-pixel.css`를 만들고 index.html의 링크와 폰트 preload 두 줄을 바꾼다.
- `--font-ui`를 Dokkaebi DNR Gothic으로. 이때 `--fs-*`를 rem 소수에서 정수 px(12·16·24…)로 바꿔야 한다 —
  도트 서체는 16의 배수가 아닌 크기에서 획이 뭉갠다. 그러라고 글자 크기를 토큰으로 모아 뒀다.
- `--img-rendering: pixelated`, `--radius-*`와 `--panel-radius`를 0으로
- 9-슬라이스 프레임은 토큰만으론 안 되고 `.module` 규칙이 하나 더 필요하다(world/ui.css의 `.frame-box`와 같은
  방식). 조각 크기 16은 frame.png 타일이 실제로 16px이라 고정이다 — 다른 값이면 테두리가 늘어나 보인다.
  ```css
  :root { --panel-bg: rgba(33, 66, 123, 1); --panel-pad: 16px; }
  .module {
      border: 16px solid transparent;
      border-image: url('../world/ui/frame.png') 16 fill / 16px round;
  }
  ```
- 차트 기하(`--line-tension`, `--point-r`, `--strip-h` 등)도 토큰이라 픽셀 톤에 맞춰 각지게 바꿀 수 있다.
  `--line-tension`이 0이면 곡선을 끄고 직선으로 그린다
- 어두운 톤으로 가면 색만 바꿔서는 안 된다 — 대비를 흰 박스 기준으로 맞춰 뒀으므로 전부 다시 재야 한다(§7)

## 1. GA와의 차별점
GA 기본 화면과 갈라지는 축은 둘이다.
- **어제 하루를 주어로 삼고, 지표마다 GA4의 확정 시점이 다르다는 걸 화면이 안다**(§3). 참여율·채널은 어제
  칸에서 빼고 확정 구간에서만 보여준다. GA는 어제 참여율 0%를 그냥 0%로 보여준다.
- **히스토리("살아있는 기록")**. 히어로의 ◀▶로 최근 28일 아무 날짜나 다시 보고, 그저께치는 재처리가 끝난
  값으로 다음 날 자동 갱신된다. GA는 그 날짜가 지금은 얼마로 확정됐는지를 다시 보여주지 않는다. 유입원 미분류
  문구가 "내일이면 채워집니다"라고 써 놓고 이 페이지 안에서 확인할 길이 없던 문제를, 문구 대신 기능으로 고친 결과다.

남은 후보는 **GA가 구조적으로 알 수 없는 것**이다. GA는 이 레포를 모른다(`/sweep`이 미니게임인 건 코너 분류로
이미 화면에 들어갔다). 검토만 하고 보류:
- **커밋 × 방문 겹쳐 보기** — 추세선에 그날의 커밋을 표시한다. `git log`만 있으면 되고 구현이 가볍다.
- **미니게임 계측** — balance·sweep·swim에 시작·클리어·이탈 이벤트를 심고 게임별 완주율을 본다. 에뮬레이터는
  이미 계측돼 있다(§4 최근 7일 인사이트).

접은 후보(2026-08-10):
- **인구통계(연령·성별)** — `userAgeBracket`·`userGender`·`brandingInterest` 모두 빈 응답이다. Google 신호
  데이터가 꺼져 있거나 트래픽이 임계값 아래라서인데, 이 규모로는 켜도 대부분 가려진다. 도시·언어·브라우저는
  값이 나오지만 GA에서 그대로 보면 되는 것들이다.
- **페이지별 상세 쪼개기** — 페이지×기기/채널/신규재방문, 랜딩페이지 이탈률 모두 API로 나오지만 GA 화면에서
  바로 볼 수 있어 옮길 값이 없다.

## 2. 구성
- 수집기(`scripts/ga4_dashboard.py`)는 `dashboard/data/<key>.js`에 `window.DASHBOARD_DATA['<key>'] = {...}`
  형식으로 쓴다. fetch가 아니라 `<script src>`로 읽어서 index.html을 파일로 바로 열어도 동작한다.
  페이지(html·css·js)는 손으로 관리하고 워크플로우는 `data/`·`archive/`만 건드린다
- 대상 하나 = GA4 속성 하나 = 데이터 파일 하나(`Target`). 대상을 늘리려면 Target을 더하고 index.html에
  `<script>` 한 줄을 넣는다. 탭은 화면이 알아서 만든다. 사이트는 호스트가 셋이라 사이트별·코너별로 나누고,
  블로그는 글 경로(`pagePath`)로 세고, 화면에 쓰는 이름만 그 경로의 가장 최근 제목(`dateHour` 기준)으로 한다.
  제목으로 세면 글 제목을 고친 날 같은 글이 두 줄로 쪼개지고 평소 대비 조회도 끊긴다. 글을 지웠다 다시 올려
  번호가 바뀌면 다른 글로 센다
- 모든 조회에서 브라우저가 `Mozilla Compatible Agent`인 세션을 뺀다(`report()`의 `NOT_BOT`). 다음(카카오) 수집기가
  검색 유입(`daum` / organic)으로 찍히는 봇이다 — 항상 맥 데스크톱·새 사용자·참여 0초·한 페이지이고 90일 동안
  예외가 없었다. 안 빼면 검색 유입 문장과 새 글의 첫날 튐이 부풀려진다. 영구 보관 파일은 원본 보존이라 거르지 않는다
- 환경변수: 자격 증명은 `GA4_SERVICE_ACCOUNT_JSON`(CI, 키 JSON 전문) 또는 `GA4_SERVICE_ACCOUNT_FILE`(로컬, 키
  파일 경로). `GA4_PROPERTY_ID`(사이트, 기본값 있음), `GA4_BLOG_PROPERTY_ID`(없으면 블로그 건너뜀),
  `FEEDBACK_SHEET_ID`(없으면 피드백 건너뜀), `GA4_OUTPUT_DIR`. 속성 ID는 시크릿이 아니다 — 서비스 계정
  권한 없이는 아무것도 못 읽는다
- 워크플로우의 `requests`는 google-auth 토큰 갱신이 쓴다. google-analytics-data가 전이 의존성으로 끌어오지만
  거기에 기대면 그쪽이 바뀔 때 조용히 깨지므로 명시해 둔다
- 모든 조회에 호스트 필터가 붙는다(`report()`가 강제). localhost·사설 IP에서 연 개발 중 방문을 빼기 위해서다
- 대시보드 페이지에는 GTM을 넣지 않는다 — 스스로를 집계하면 제 방문으로 부푼다
- 사이트 페이지 이름은 `pageTitle`에서 공통 접미사 `" : atah.io"`를 잘라 쓴다(pc98·suiko에는 코너 분류가
  없어 경로만으론 읽을 수 없다). 코너 분류에서 `/scene_viewer`는 옛 경로라 이름이 `/viewer`와 같아야 이력이
  한 코너로 이어진다
- 밑줄로 시작하는 키(`_visitorsByDay`·`_priorSources` 등)는 인사이트 계산용 중간 재료라 파일에 싣지 않는다
- history 항목에는 날짜에 딸린 값만 담는다(`HISTORY_KEEP`). `daily`·`meta`·`settled`·`hourPattern`·`months`는
  최상위에만 있고, 과거 날짜 화면은 최신 것을 빌려 쓴다. 최신 날짜도 history에 들어 있어서 날짜 목록의 마지막이
  늘 최신이다. history는 28일만 남긴다
- 히스토리 일괄 채우기 `scripts/ga4_backfill_history.py`: 기본은 age 3~28 중 비어 있는 날짜만 채우고,
  `--refresh`는 age 2~28을 전부 다시 써서 수집 로직을 고친 뒤 얼어 버린 값을 바로잡는다(`key` 달린 인사이트는
  넘겨받는다). 자격 증명·환경변수는 수집기와 같다
- `.githooks/pre-push`는 클론마다 `git config core.hooksPath .githooks`로 켠다. origin의 history 날짜를 로컬이
  다 갖고 있는지, 최상위 `yesterday` 날짜가 뒤로 가지 않았는지(날짜 집합만 보면 이 후퇴를 놓친다), 보관 파일
  날짜가 빠지지 않았는지 본다. 28일 창 밖으로 자연히 밀려난 날짜는 빼고 비교한다 — 안 그러면 며칠 전 push의
  옛 날짜를 유실로 오탐한다. 훅의 `TREND_DAYS`는 수집기와 같은 값이어야 한다. 급하면 `SKIP_GA4_CHECK=1 git push`

## 3. 지표마다 다른 확정 시점
GA4는 어제치를 아침에 확정하지 않는다 — 세션 속성(채널 그룹, 참여 세션)을 하루 이상 뒤에 재처리한다. 어제
참여 세션 0에 채널 대부분이 Unassigned인데 그저께는 정상인 식이다. 그래서 지표를 신뢰도로 나눈다.
- 개수(사용자·세션·조회수와 그 분해): 어제치를 쓰되, 첫 수집값은 덜 찬 날이 있어 다음 날 다시 받아 정정한다(§10)
- 세션 속성(참여율·평균 체류): 재처리가 끝난 구간(`SETTLED`, 어제를 뺀 7일)에서만 본다. 날짜 무관이라
  history에 싣지 않고 과거 날짜 화면에선 안 보인다
- 유입원: 어제치를 쓰되 미분류(`(not set)` 등)를 목록에 섞지 않고 따로 센다. 섞으면 대개 그게 1위가 된다

히스토리 갱신은 그저께(`HISTORY_REFRESH_AGE` = 2) 한 번이다. 유입원 미분류는 하루~이틀 뒤 다시 보면 거의 다
풀려 있었다(2026-08-18 대조). 일주일이 지나도 조금 남는 날은 리퍼러 없는 방문처럼 영영 분류가 안 되는 종류다.

## 4. 인사이트
원칙: **화면에 이미 있는 숫자를 되풀이하지 않는다.** 비교(평소 그 페이지는 몇 회였나)와 분해(누가 그 조회수를
만들었나)만 말한다. 할 말이 없으면 줄 수가 줄어드는 게 정상이다. 기록 문장도 히어로에 있는 그날 값은 다시 쓰지
않고 "가장 적습니다(다른 날 최저 11명)"처럼 기록이라는 사실과 비교 상대만 말한다. 같은 이야기를 두 문장으로
나누지 않고, 문장을 내는 조건을 문장에 다시 읽어 주지 않는다.
- 요약 박스는 "그날"과 "최근 7일" 두 묶음이다. 최근 7일 문장은 `span: "week"`가 달리고(`key`가 있는 옛 문장도
  같이 친다), 묶음 제목이 기간을 말하므로 문장 앞에 "지난 7일"을 붙이지 않는다. 과거 날짜에선 "{날짜}까지 7일"이다
- 게임 플레이는 요약 문장이 아니라 별도 표 박스다(§6)
- 문장마다 먼저 볼 곳을 `**…**`로 감싸고, 화면이 문장을 이스케이프한 뒤 이 표시만 `<b>`로 바꾼다. 수집기에서
  HTML을 만들지 않는다
- history에 얼리는 문장은 "어제" 대신 날짜("08.15")로 쓴다 — 얼린 "어제"는 나중에 거짓말이 된다. 화면도 과거
  날짜에선 같은 규칙을 따르고, 히어로 제목만 옆의 날짜 태그와 겹치지 않게 "{n}일 전"으로 쓴다. 이 n은 반드시
  최신 날짜(`latestDate`)와의 차이로 구한다 — 과거 스냅샷의 `yesterday`는 그 날짜 자신이라 그걸 쓰면 늘 1이 나온다
- 할 말이 없으면 "평소와 크게 다른 점이 없었습니다"라고 말한다(빈 자리는 고장 난 것처럼 보인다). 단 14일이
  안 쌓였으면 기준이 얇다고 말한다

**28일 분포**(히어로 배지·등수·기록 문장의 자)는 대상 날짜에서 끝나는 28일로 잰다. 그저께를 다시 쓸 때도
그 날짜 기준 창을 따로 조회한다(2026-10-25, 예전엔 늘 어제로 끝나는 창이라 하루 뒤 날까지 섞였다).

**기록일 때만 말한다**(2026-09-26). "한 사람당"·재방문자 몫·방문자 수 문장은 그날이 나머지 날보다 엄밀히 높거나
낮을 때만 낸다(동률이면 침묵). q1~q3 밖을 조건으로 두면 정의상 절반의 날이 걸려 격일로 나왔고, 범위 밖이라는
사실은 히어로 배지가 이미 말한다. 비교 상대에서 그날을 빼야 한다 — 안 빼면 새 기록인 날 "그 전 최고"가 제 숫자로 나온다.
- 재방문자 몫은 조회수로 잰다. 사용자 수는 구간마다 중복 제외라 신규+재방문+미분류가 총계와 안 맞는다. 1인당
  장수로 견주지 않는 것은 조회 없이 참여만 잡힌 사람 때문에 "재방문 0.5장" 같은 착시가 생겨서다. 미분류가
  20% 넘게 섞인 날은 비교에서 뺀다
- 깊이 문장(한 사람당·재방문자 몫)은 그날 방문자가 적거나(`MIN_USERS_FOR_DEPTH`) 신규·재방문 한쪽이
  한 명뿐이면(`MIN_GROUP_USERS`) 내지 않는다 — 한두 명의 습관을 그날의 성격처럼 말하게 된다

**튐 판정은 수집기 한 곳에서만 한다**(`ydayPages[].spike`). 표의 배율 표시와 인사이트 문장이 같은 값을 쓴다 —
따로 재면 언젠가 "표에는 튀었는데 문장은 침묵"하는 상태가 된다.

**배율의 분모는 최소 1회**(`RATIO_FLOOR`, 2026-10-02). 평소 대부분 0이고 가끔 1인 페이지에 "꾸준히 보던 양의
수십 배"라는 그림은 맞지 않고, 분모가 작을수록 조회 한두 번 차이로 배율이 크게 흔들린다. 튄 행의 상당수가 평소
1회 미만 페이지였다(특히 블로그). 분모를 1로 깔아도 튄 행의 집합은 그대로다(5회 이상이면 1회 미만 페이지는
어차피 5배 이상). 표의 "평소/일" 칸은 1회 미만을 `<1`로 쓰고, 화면은 1보다 작은 평균을 반올림하지 않는다.
인사이트는 배율 대신 늘어난 조회수(어제 − 평소)가 가장 큰 페이지를 고른다 — 배율로 고르면 분모가 작은 드문
페이지가 매번 이긴다. 평소 1회 미만이 뽑히면 배율 없이 "평소 하루 1회도 안 보던 페이지"라고만 말한다.
앞선 구간 조회가 0인 페이지도 같은 조건으로 튐이 될 수 있고, 문장은 "전에 조회가 없던 페이지"다 — 빼 두면 새 글이
첫날 아무리 읽혀도 "평소와 크게 다른 점이 없었습니다"가 나온다. 표의 "평소/일" 칸은 이때 배율 없이 "처음"이다.
첫 조회가 앞선 구간 안에서 최근 7일 이내에 생긴 페이지(`fresh`)도 "평소"를 말하지 않는다 — 발행 직후 며칠치를
27일로 나눈 값은 평소가 아니어서 "평소 하루 1회도 안 보던 페이지"가 틀리게 나왔다. 문장은 "{날짜}에 처음 조회가
생긴 페이지"이고 표의 칸은 마찬가지로 "처음"이다. 튐 판정 자체는 그대로다

**튐과 증가를 가른다**(2026-10-02). 27일 평균은 오르는 흐름을 늦게 따라가서, 며칠째 늘던 페이지가 매일 "N배로
뛰었다"로 나왔다.
- 튐: 27일 평균의 2배이면서 **최근 7일 평균의 2배**이기도 해야 한다(`RECENT_DAYS`). 이미 올라 있는 페이지는 그
  수준에서 또 뛰어야 튐이다
- 증가(`rising_state`): 최근 7일 하루 평균이 `RISING_MIN_AVG` 이상, 그 전 21일 평균의 `RISING_RATIO`배 이상,
  창 안 7일 평균 중 기록, 7일 중 `RISING_MIN_DAYS`일 이상이 그 전 평균보다 높음(하루 큰 튐 하나가 평균을 끌어올린
  걸 증가로 치지 않게)
- 같은 페이지의 증가는 한 번 알리면 7일 동안 다시 말하지 않는다. 오르는 동안엔 7일 평균이 매일 기록을 세운다.
  직전 7일의 상태를 **같은 28일 창 길이로** 재야 한다 — 창이 짧아지면 앞쪽의 높았던 날이 빠져 가짜 증가가
  잡힌다. 그래서 페이지별 일별 조회는 34일치를 받는다
- 튄 페이지가 그날 증가도 시작하면 문장 하나로 합친다
- "나머지 N곳은 평소보다 조용했습니다" 꼬리는 뺐다. 조회가 적은 페이지는 평균이 몇 번 몰린 날에 끌려 올라가
  있어 평균보다 적은 날이 보통이라, 거의 매일 참이었다

블로그의 목록성 페이지는 `ydayPages[].list`로 표시해 표에 "목록" 태그를 달고 튐·증가 문장에서 뺀다 — 글이 아니라
목록을 넘겨 본 흔적이다(`LIST_PAGE_RE`: 카테고리·태그 글 목록, 태그 모음, 방명록). 블로그 첫 화면은 들어오는
입구라 그대로 둔다.

새 유입원 문장은 대상 이름을 앞에 붙이고, 비교도 대상 안에서만 한다 — 사이트와 블로그는 GA 속성이 따로라 한쪽의
첫 유입이 다른 쪽에서 이미 여러 번 온 출처와 헷갈리게 읽혔다. GTM 미리보기로 연 내 방문(`DEBUG_SOURCES`)은 새
유입원으로 치지 않는다.

미분류 유입이 절반을 넘으면 경고하는데, 문장이 `confirmed`로 갈린다. 갱신 전이면 "내일 다시 확인됩니다"가
참말이고, 갱신을 거쳤는데도 남아 있으면 재처리 지연이 아니라 계측 문제일 가능성이 커서 다른 말을 한다 — 더 이상
재확인이 없는데 "다시 확인됩니다"라고 하면 지키지 못할 약속이 된다. 화면의 유입원 단서 줄도 같은 규칙이다.
합계를 "세션 수"라고 부르지 않는다 — 한 세션에 출처가 여럿 붙어 유입원별 합이 총 세션을 넘는다.

조사(`josa`)는 끝의 괄호 덩어리를 통째로 건너뛰고 판정한다("…(from DSアニメ総集編'98)" → "애니메이션이").
숫자로 끝나면 한국어 독음 받침으로 가린다. 영문으로 끝나면 끝 글자로 어림한다 — 모음·y·w·r는 받침 없음
("OYSTER BAY가"), l·m·n은 받침 있음, 그 밖은 두 형태를 함께 쓴다. 날짜 라벨("09.20")은 "이십일"처럼 읽혀 늘
"은"이다. 사이트의 "기타" 코너는 이름으로 쓰지 않고 페이지 제목을 쓴다.

**최근 7일 인사이트**(2026-10-25, `fetch_weekly`·`weekly_insights`). 하루 수십 명 규모에선 유입 경로·검색
흐름이 하루치로는 안 보여서 최근 7일 단위로 말한다. 날짜 무관("지금 기준")이라 최신 수집에서만 계산하고 그날
기록에 같이 얼린다. 어제치는 잠정이라 마지막 하루가 조금 덜 찬 채로 들어간다.
- 유입 경로 변화: 직접·다른 사이트 링크·소셜 채널의 7일 세션이 그 전 7일의 2배 이상 또는 절반 이하이고 차이가
  15세션 이상이면 말한다. 가장 많이 늘거나 준 호스트와, 늘었을 때는 그곳의 재방문 비율을 붙인다. 호스트별
  세션은 여러 호스트를 오간 세션을 각각 세서 합이 채널 합과 꼭 맞지는 않는다. 직접 방문이 몇 배로 는 주에
  (대부분 suiko 재방문자) 화면이 한 줄도 말하지 않았던 것이 계기다. 한 채널이 늘고 다른 채널이 줄었는데 가장
  크게 움직인 호스트가 같으면 한 문장으로 합친다 — 같은 사람들이 링크 대신 직접 오게 된 이야기를 두 번 했다
- 검색: 7일 검색 세션이 그 전 3주 주평균의 1.5배 이상이거나 절반 이하이고 차이가 5세션 이상이면, 엔진별로
  나눠 말한다. 검색 채널은 이 문장이 맡아서 유입 경로 변화 문장에서는 뺀다
- AI 어시스턴트: 7일 세션이 그 전 3주 어느 주보다 많으면 말한다. 같은 출처를 새 유입원 문장이 이미 말했으면 뺀다
- 유입 경로·검색·AI 문장은 한 번 말하면 7일 동안 다시 말하지 않는다. 문장에 `key`(예: `channel:Direct:up`,
  합친 문장은 공백으로 이은 둘)를 달아 기록에 남기고, 다음 날부터 최근 7일 기록에 같은 `key`가 있으면 건너뛴다. 그저께치를 다시 쓸 때
  (`HISTORY_REFRESH_AGE`, `--refresh`)도 `key`가 달린 문장은 지우지 않고 넘겨받는다 — 안 그러면 다음 날 기억이
  사라져 매일 같은 말을 한다. 흐름이 7일 넘게 이어지면 일주일에 한 번 다시 말한다

남은 것:
- **과거 날짜 화면의 추세선·시간대 패턴은 최신 28일을 빌려 쓴다** — `daily`·`hourPattern`이 최상위에만 있어서다.
  배지·등수·띠의 기준(`baseline`)은 그 날짜의 창으로 잰 값이라, 과거 날짜에선 띠와 선의 창이 서로 다르다.

## 5. 최장 방문
GA4 Data API는 세션을 낱개로 주지 않는다(세션 ID 차원이 없고 체류 시간은 평균뿐). 그래서 **세션 내내 값이 안
바뀌는 차원**(`LONGEST_DIMS`)으로 잘게 쪼개, 세션이 1건만 남은 칸의 "평균"을 그 세션의 체류 시간으로 읽는다.
관문 둘을 못 넘으면 그날은 값을 남기지 않는다.
- 정합성: 쪼갠 세션 수·총 체류의 합이 원본과 같아야 한다. 다르면 한 세션이 여러 칸에 흩어져 1건짜리 칸이 조각일 수 있다
- 확정: 2건 이상 뭉친 칸의 합계(세션 수 × 평균)가 그 칸의 상한이다. 찾은 최댓값이 모든 상한 이상이어야 진짜 최댓값이다

통과 못 하는 날이 흔하다. 어제치는 유입원이 안 굳어 세션이 여러 칸으로 쪼개져 거의 늘 탈락하고, 그저께 갱신 때
대개 살아난다. 여러 날을 한 번에 쪼개면 칸마다 세션이 뭉쳐 관문을 못 넘으므로 하루 단위로만 부른다. 같은 조건을
필터로 걸어 통째로 조회해 보면 세션 1·사용자 1이고 이벤트 시각 차도 계산값과 맞았다 — 부스러기가 아니라 실제
한 사람의 한 방문이다. 화면의 확정 구간 칸은 날짜마다 얼려 둔 값 중 최댓값을 고르므로, 7일이 다 탈락하면 안 나온다.

## 6. 화면
**하루치를 덜 믿는 쪽으로**(2026-10-02). 하루 방문자가 한두 자릿수인 규모에서 어제 하루를 잘게 나누면 화면이
대부분 우연을 읽는다.
- **히어로 배지 "많은 편/적은 편"**: 가운데 절반(q1~q3) 밖이면 붙이던 때는 네 칸 모두 이틀에 하루꼴로 붙었다.
  기준을 10·90 백분위(`BAND_PCT`)로 넓혔다. 추세선 뒤 띠도 같은 구간이라 점과 배지가 어긋나지 않는다
- **시간대**: 하루 세션 수십 건을 24칸에 나누면 대부분 0~3이다. 최근 28일 시각별 하루 평균(`hourPattern`)을
  옅은 막대로 깔고 어제를 그 위에 진한 막대로 겹친다. 크기는 색이 아니라 길이로 말한다 — 6단계 색 램프를 썼을 땐
  값 종류가 서너 개뿐이라 서너 색만 쓰였고, 빈 칸과 아주 작은 값이 같은 색으로 뭉갰다. 막대 뒤에 트랙을 깔아
  "아무도 안 왔다"와 "칸이 없다"를 가른다
- 시간대 합은 그날 세션 수보다 크다. GA4가 여러 시간에 걸친 세션을 시간마다 센다. 시작 시각(session_start)으로
  세면 합은 맞지만 재처리 전인 어제치는 오히려 크게 틀려서, 값은 그대로 두고 설명을 사실대로 적는다
- **긴 흐름**: 월별 하루 평균 방문자(`months`)와 최근 7일 vs 그 전 7일(`weekCompare`). 하루 평균이라 덜 찬
  달도 같은 자로 견준다. GA는 방문 0인 날을 행으로 주지 않아 날짜를 직접 채워 0으로 센다 — 안 채우면 그런 날이
  있는 달이 "덜 찬 달"로 잡히고 평균이 부푼다. 날짜 무관이라 최신 화면에만 나온다
- **일별 추세(`daily`)도 빈 날을 0으로 채운다**(2026-10-07). 첫 행부터 대상 날짜까지 채우고, 앞쪽(측정 전일 수
  있는 구간)은 채우지 않는다. 빈 날이 빠지면 대상 날짜를 창의 위치로 고르는 탓에 라벨이 하루씩 밀린다 — 블로그
  방문 0인 날 하나로 history 날짜가 밀린 적이 있다
- "방문자"(활성 사용자)와 "새로 온 사람"(전체 사용자 기준)은 기준이 달라 드물게 신규가 더 많다. 그런 날은 보조줄을
  뺀다 — 값을 깎아 맞추면 없는 숫자를 만드는 셈이다
- "최근 N일"·"평소/일 N일 평균"의 N은 `meta.trendDays`(요청한 일수)가 아니라 실제로 받은 `daily` 길이로 쓴다.
  속성이 어린 대상에서 거짓말을 하게 된다
- 페이지 이름 우선순위: 코너(atah.io 안) → 페이지 제목 → 경로. 제목으로 바꿔치기한 경우에만 경로를 보조줄로 남긴다.
  호스트는 이름 옆에 작게 붙인다(제 줄을 차지하면 같은 호스트가 행마다 반복된다)
- **게임 플레이**: 에뮬레이터 이벤트(pc98·suiko)로 게임마다 시작·세이브·이어하기 인원과 도달한 가장
  긴 플레이 시간 단계를 표로 보인다(`games`). 칸마다 그날 값 옆에 그날까지 7일 값을 옅게 붙인다 — 7일 합만
  보이던 때는 그날 무슨 일이 있었는지 묻혔다(2026-10-30). 날짜에 딸린 값이라 history에 얼리고, 그 전 28일도
  같은 조회로 채워 넣었다. 사람 수는 각 기간 안에서 중복 제외이고, 계측 이벤트는 각 게임 레포 NOTES에 있다.
  문장으로 요약에 넣었을 땐 게임 셋을 한 줄에 이어 붙여 읽히지 않았다. 게임 이벤트가 없는 블로그엔 나오지 않는다
- 과거 날짜 화면에선 날짜 무관인 모듈(확정 구간·미확인 피드백·긴 흐름)을 빼고, 문장 속 "어제"를 그 날짜로 바꾼다 —
  현재 시점 값을 과거 화면 옆에 두면 시점이 섞인다
- 데이터 멈춤 경고: 마지막 갱신이 KST 오늘보다 2일 이상 전이면 띄운다(그날 실행 전엔 1일 차라 오탐이 없다).
  대상이 여럿이면 가장 오래된 쪽 기준

**차트 규칙**
- y축은 하나만. 크기가 다른 두 지표를 한 그림에 겹치지 않는다
- 색은 항목의 정체성을 따른다. 순위가 바뀌어도 같은 항목은 같은 색
- 크기(많고 적음)는 파랑 한 색의 명도로만 표현한다
- 많고 적음을 좋고 나쁨의 색으로 칠하지 않는다. 방문자가 적은 날이 나쁜 날은 아니므로 "평소 범위 / 많은 편 /
  적은 편"이라는 말로만 쓴다. 증감색 토큰을 두지 않고, `--attention`은 지표가 아닌 상태(미확인 피드백·데이터
  멈춤)에만 쓴다
- 캔버스로 그린 것에는 같은 값을 읽을 수 있는 표가 함께 있다. Chart.js(CDN)를 못 불러오면 차트만 포기하고 표를
  펼친다 — 그대로 `Chart.defaults`를 건드리면 스크립트 전체가 멈춰 화면이 통째로 빈다
- 캔버스 차트는 패널이 보인 뒤에 만든다. 숨은(display:none) 칸에서 만들면 크기가 0으로 잡혀 찌그러진다
- 새 시각 상수는 JS에 박지 말고 theme.css에 토큰으로 만든다(캔버스는 CSS가 닿지 않아 JS가 토큰을 읽는다).
  토큰이 없으면 기본값으로 그려 차트가 통째로 사라지지는 않는다
- 추세선은 `--accent`로 긋는다 — 주색(`--brand`)은 2px 선으로는 흰 배경에서 대비가 모자라 띠 위에서 윤곽을
  잃는다. 면은 주색 그대로. 곡선은 monotone — 기본 cubic은 뾰족한 날에 점 바깥으로 튀었다 돌아온다
- 선 끝 직접 라벨은 두 선이 글자 한 줄보다 가까우면 그리지 않고 범례에 맡긴다

## 7. 레이아웃·테마
**겹침 검증**(2026-08-14). Claude in Chrome으로 500px·1400px 폭 모두 가로 스크롤이 없는 것을 실측했다. 방어
수단: 표는 `.scroll`(overflow-x: auto)로 감싸고, `.module`에 `min-width: 0`, 캔버스·SVG에 `max-width: 100%`.
페이지 표는 숫자 칸에 `width: 1%`를 줘 이름 칸이 남는 폭을 다 가져간다(안 그러면 이름과 숫자가 표 양 끝으로 벌어진다).

스킨을 새로 얹을 때 다시 볼 함정:
- 격자는 `.panel`에 건다. `.dash-main`에 걸면 모듈이 손자가 되어 격자에 못 들어간다
- 박스는 제 내용만큼만 높다(`align-items: start`). 줄 안에서 키를 맞추면 짧은 박스가 긴 박스에 끌려 안이 텅
  빈다. 맨 위 두 박스만 `.stretch`로 키를 맞춘다
- `.panel[hidden]` 규칙은 `.panel`의 display와 짝이다 — 없으면 숨은 탭이 보인다
- 좁은 화면에서는 `.module`만이 아니라 격자의 모든 자식의 span을 되돌린다. 모듈 아닌 자식에 span-12가 남으면
  1칸 격자에 암시적 열이 생겨 배치가 어긋난다
- `.module-note`를 `.module` 안으로 한정하지 않는다 — 모듈 밖 설명문이 기본 `<p>`로 나와 제목보다 커진 적이 있다
- 구획 제목은 설명문과 크기는 같게 두고 굵기·색으로만 한 겹 올린다. 셋 다 같게 했더니 제목과 설명이 한 덩어리로 읽혔다
- 인사이트에 `max-width`를 두지 않는다. 박스 안이라 글이 박스 절반만 채운다
- flex 안에서 margin과 gap을 같이 쓰면 간격이 이중으로 붙는다
- 박스가 전부 같은 무게면 무엇부터 볼지 알 수 없어서, 어제 스탯 박스 하나만 면을 밝히고 테두리를 또렷하게 한다

**테마**는 밝은 톤이다. 사이트의 다른 페이지는 어두운 톤인데, 매일 아침 오래 들여다보는 화면이라 밝은 쪽을 택했다.
색은 흰 박스(#fff) 기준으로 대비를 검증했다(그래픽 3:1, 본문 4.5:1).
- `--text-muted`는 본문 기준을 겨우 넘기는 값이라 더 밝히면 안 된다
- 주색(`--brand`, 사이트 링크색)은 흰 배경 대비가 낮아 얇은 선·작은 글자로는 못 쓰고 큰 면(시간대 막대, 추세선 아래
  면, 점유율 최대 조각, 강조 박스)만 맡는다. 선·마크·링크는 같은 색상각의 진한 형제 `--accent`가 맡는다
- 시리즈 색의 앞 셋(사이트 호스트 3개)은 주색 계열의 명도 단계다. 빨강·갈색을 중간에 넣으면 적색약에서 진회색과
  붙는다. 뒤의 셋은 호스트가 늘 때를 위한 예비다
- 띠(`--band`)와 순위 막대는 데이터보다 확실히 옅어야 한다 — 진하면 띠가 데이터로 읽히고, 막대 위 글자가 안 읽힌다

GitHub 문서는 부하가 높으면 대기 중인 작업을 버릴 수도 있다고 하지만, 이 저장소에서 실제로 빠진 날은 아직 없다
(빠졌다고 기록했던 날도 늦게 떴을 뿐이었다). 급하면 수동 실행(`gh workflow run ga4-dashboard --repo
flvrdoyster/ataho`)으로 메꾼다 — 수동 실행은 지연 없이 바로 뜬다.

**수집 시각을 늦춰도 어제 참여율·채널은 안 채워진다** — GA4의 재처리는 시각이 아니라 주기의 문제라서, 저녁에
돌려도 어제치 세션 속성은 여전히 비어 있다. 그래서 참여율·체류시간은 확정 구간에서만 보여주고, 유입원은 그저께치를
다음 날 한 번 더 조회해 히스토리에 덮어쓴다(§3).

**방문자·조회 같은 개수도 첫 수집 때는 덜 찬 값일 수 있다**(2026-10-20). 수집은 일이 끝나고 반나절쯤 지나 도는데,
그때 GA4가 어제 저녁 이후 이벤트를 다 못 모은 날이 있다 — 첫 수집값이 확정값의 절반 가까이 모자란 날도 있었고,
블로그는 모자란 날이 더 잦다. 일이 끝나고 하루 넘게 지난 값은 확정값과 같았다. 내일 아침 수집이 그저께치를 다시
받아 기록·인사이트·보관 파일을 정정하므로 값은 하루 뒤 바로잡힌다 — 확인한 결과 어제를 뺀 모든 날의 기록·추세선·
보관 파일이 일치했다. 그래서 수집 시각을 늦추거나 두 번 받지 않고, 어제 칸이 있는 첫 줄에 "잠정이라 내일 아침
수집 때 바로잡힙니다"만 적는다(`data.confirmed`가 거짓일 때). 예약 실행이 하루 통째로 빠지면 그날 기록은
정정되지 못한다. 보관 파일은 최근 10일을 덮어써서 이 경우에도 보호된다.

실시간에 가까운 카운터를 원한다면 주기를 늘려야 하고, 그만큼 데이터 파일 자동 커밋도 늘어난다(3시간마다 = 하루 8건).

**로컬 세션과의 충돌**: 워크플로우가 origin에 매일 직접 커밋하는 동안 로컬 세션은 며칠 전 지점에서 기능을 쌓기
쉬워, `dashboard/data/*.js`에서만 머지 충돌이 반복됐다(2026-08-18 실제 발생). `.gitattributes`의 `merge=ours`로
이 파일들은 항상 로컬을 유지하고 충돌 표시 없이 넘어간다 — 단 신선도를 비교하지 않으므로, 머지/푸시 전에
`ga4_dashboard.py`를 한 번 재실행해 로컬 데이터를 최신으로 만들어 두거나 pre-push 훅에 맡겨야 한다. 클론마다
`git config merge.ours.driver true`를 한 번 등록해야 실제로 동작한다. CI는 머지하지 않아 필요 없다.
